# AI interpretation layer: natural language to AzeMark

Status: proposed, not scheduled. This document is the input to a wayfinder map; the
map and its child tickets are not created yet.

The compiler already renders AzeMark into HTML, SVG, PNG, PDF and the optional TeX
profiles. What is missing is the front of the pipeline: a user describes a document
and gets editable AzeMark back. The interpretation layer is that step, and the
compiler stays exactly as deterministic as it is today.

[`azeforge-product-blueprint.md`](azeforge-product-blueprint.md) already fixes the
principle in §21: the core compiler must not embed an LLM, AI is an optional provider
layer, and provider support ships as separate packages. This plan works out what that
means against the code that actually exists.

## What the compiler already provides

Measured against `@aruzone/aze-forge` 0.5.0, built from this checkout.

| Artifact | Size | Use in prompting |
|---|---|---|
| `azeforge grammar --json` (`buildGrammarDocument`) | 87,353 bytes total; 0.7 to 20 KB per directive | versioned machine-readable grammar, and `buildGrammarDocument({ directive })` already scopes it |
| `azeforge capabilities --json` | 24,117 bytes | what this release can render: plugins, block renderers, renderers, themes, formats, limits, security policy |
| `docs/language/*.aze.md` | 110,197 bytes over 14 documents, 1.6 to 15 KB each | compile-verified exemplars, graded from minimal to deepest feature per family |
| `Diagnostic.suggestion` and `Diagnostic.fix` | per diagnostic | machine-applicable repairs, `applicability: "safe"` with explicit edits |
| `formatSource()` / `azeforge format` | | canonicalization that preserves meaning |
| `compiler.validate()` and `compiler.parse()` | cheap | the verification channel for the repair loop |
| `compiler.render*()` | not cheap, needs the pinned browser | out of scope for the loop |

The web product already reuses the same language corpus for its preloaded examples
(`src/web/examples.json`, regenerated by `scripts/examples.mjs`). That reuse is the
precedent for treating the corpus as a first-class machine input rather than
documentation.

The per-directive sizes are the load-bearing number. Geometry is 20,283 bytes and
circuit is 16,892, against 765 for `figure` and 853 for `formula`. The full grammar
report is roughly 22k tokens, which is not a system prompt. Directive-scoped
retrieval is required, not an optimization.

## Decisions

### Generate AzeMark text, not JSON or an AST

AzeMark is already the interchange format, and the compiler is already the validator.
Emitting AST JSON would create a second schema to keep in sync with `grammar.json` and
a second repair channel to maintain. The model writes source; the compiler decides
whether it is any good; the user edits it before anything is exported.

One consequence worth stating plainly: model-reported confidence is discarded.
Confidence is a diagnostic-free `validate()` result, nothing else.

### A separate package, never the compiler

```
@aruzone/aze-ai             provider-neutral core: grounding, pipeline, repair, evaluation
@aruzone/aze-ai-anthropic   provider adapter
@aruzone/aze-ai-openai      provider adapter
@aruzone/aze-ai-ollama      provider adapter (local, offline-capable)
```

Names follow blueprint §21. The core holds no weights, opens no connection of its own,
and is runtime-agnostic ESM so the CLI and the browser can run the same code. Provider
adapters own the network.

### Retrieval over compiler-owned artifacts, not a hand-written prompt

Prompt assembly reads from the compiler's own published surfaces, all versioned:

1. a directive index derived from `grammar.json`, used to classify the request;
2. the full grammar fragment for each selected directive;
3. the capabilities digest, so the model cannot propose a block this release lacks;
4. one or two exemplars from the matching `docs/language/` document;
5. the diagnostic registry, attached only during repair.

A prompt is then pinned to a grammar schema version and a capabilities fingerprint,
which is what makes a generation result reproducible enough to debug. The anti-drift
gate is the same shape as `test/grammar.test.mjs`: the description and the compiler it
describes are checked against each other.

### A staged pipeline, not one-shot generation

The pipeline mirrors the Document and Block model the compiler already has:

```text
instruction
  -> outline            front matter, heading skeleton, block plan
  -> blocks             one generation per planned Block, that directive's grammar injected
  -> assemble           concatenate in authored order
  -> format             formatSource(), canonical spacing and fences
  -> validate           compiler.validate()
  -> repair             bounded: safe fixes, then model re-emission with diagnostics
  -> Editor             user reviews, edits, then exports through the existing path
```

Short requests degenerate to a single Block. Long documents get progressive rendering
as Blocks arrive. Nothing exports without the user accepting the source.

### Web: browser-side provider, service stays offline

The web deployment is explicit that nothing in the container opens an outbound
connection, and that the block belongs to the host firewall, not to the image (see
[aze-forge-web deployment](https://github.com/aruzone/aze-forge-web) and its README).
Service-side provider calls would repeal that envelope and drag in secret injection,
egress allowlisting, new deadlines and limits, and a content-privacy statement.

The cheaper path for a single-user, token-gated alpha is the browser calling the
provider directly with a user-supplied key held in tab session storage. The compile
service keeps its current operation set of `analyze`, `compile` and `format`, and the
repair loop crosses the boundary through the existing job protocol: generate in the
browser, validate through the service, re-prompt with the diagnostics.

The cost is small and known: `connect-src` has to be added to
`FRONTEND_CONTENT_SECURITY_POLICY` in `src/service/static.mjs`, which is currently
`default-src 'none'` with `script-src 'self'`, and the pinned AI core has to be served
as a static module the way `examples.json` is.

## Interfaces

```ts
interface Provider {
  readonly id: string;
  readonly model: string;
  complete(request: {
    system: string;
    messages: readonly Message[];
    signal?: AbortSignal;
  }): Promise<string>;
}

interface GenerateRequest {
  instruction: string;
  directives?: readonly string[];   // skip classification when the user knows
  maxRepairAttempts?: number;       // default 2
}

interface GenerateResult {
  source: string;                    // AzeMark text, always shown before export
  diagnostics: readonly Diagnostic[]; // final validate() output
  attempts: readonly RepairAttempt[]; // each round's diagnostics, kept for debugging
  grounding: {
    grammarSchemaVersion: string;
    capabilitiesFingerprint: string;
    exemplars: readonly string[];
  };
  provenance: { provider: string; model: string; promptHash: string };
}
```

`provenance` is a sidecar. It must not enter the Document: front matter participates in
the content hash, so generation metadata written there would make two identical
documents hash differently.

## Surfaces

### CLI

```bash
azeforge generate "a lecture note on RC filters with one schematic and a Bode plot" \
  --output draft.aze.md

azeforge generate --directive equation --output eq.aze.md
cat instruction.txt | azeforge generate --json > result.json
```

Provider, model and key come from the environment. Exit codes follow the existing
vocabulary in `src/help.ts`: 0 when the result validates, 1 when generation ran but the
result still fails validation, 2 for usage errors. Without explicit provider
configuration the command refuses to run. Content does not leave the machine by
accident.

### Web

A "Describe" panel beside the Source pane. The prompt is user input, the returned
source lands in the editor, and every repair round reuses the job protocol that
`src/service/jobs.mjs` already implements. No new service middleware and no protocol
version bump.

## Repair loop policy

Only `DiagnosticFix` edits marked `applicability: "safe"` are applied without asking.
Everything else is a model re-emission with the diagnostics attached, or a user
decision. The loop is bounded by both attempts and a wall-clock ceiling.

Source that does not validate is never presented as finished. This is the same line the
language contract already draws: the compiler refuses to silently repair semantics, so
the interpretation layer cannot either.

## Determinism and privacy

Generation is non-deterministic and stays outside every determinism claim. The
canonical suites in `test/*.test.mjs` and `scripts/acceptance.mjs` must not gain a
generation gate. The layer gets its own harness, and its results are recorded.

Determinism resumes the moment a source is accepted: same source, same compiler
version, same artifact. That is the property worth testing.

Privacy rules follow blueprint §22: never send content to a provider without explicit
configuration, display which provider will receive it, keep an offline mode, and keep
prompts and source out of service logs, which are metadata-only today.

re-pinning the web dependency comes before or with the web work, not after.

## Acceptance

- A corpus of natural-language requests produces source whose first-pass
  `validate()` result is measured and recorded. The owner sets the threshold with that
  number in hand.
- Every failure reports diagnostics that name a line and a remedy.
- The repair loop never publishes source that failed validation.
- The compile path opens no network connection, with or without the AI packages
  installed.
- An accepted source reproduces its artifact deterministically.
- Generated source is visible and editable before any export.

## Open questions for the wayfinder

1. Which model class is the floor? The native mathematics grammar and the record-list
   directive bodies are the hard parts, and the prototype exists to find the answer.
2. Does the `language-guide` surface ship in the compiler package, or as a generated
   artifact in the AI package built from `grammar.json`?
3. Browser-direct providers need CORS support and, for some vendors, an
   explicit browser-access opt-in. Does that hold for every provider we intend to
   support, or does the alpha ship one provider and stop there?
4. Is there a managed-hosted generation path at all, or is the alpha strictly
   bring-your-own-key plus local Ollama?
5. What is retained locally after a generation, if anything? Attempts and diagnostics
   are useful for debugging and also a copy of user content.
